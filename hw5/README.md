# HW5. Online Cinema

Pipeline аналитики онлайн-кинотеатра на Python: Movie Service → Kafka → ClickHouse. Сервис агрегации читает события из ClickHouse, сохраняет дневные снимки там же для Grafana и выгружает готовые метрики в PostgreSQL. Завершённые дни экспортируются из PostgreSQL в S3-совместимый SeaweedFS.

## Запуск

Из папки `hw5`:

```bash
docker compose up -d --build --wait
```

Нужен Docker Compose v2. При первом запуске загружаются образы, Python-зависимости и плагин Grafana. Сервис `bootstrap` создаёт топик, регистрирует схему, применяет SQL и создаёт бакет. Остальные сервисы стартуют после успешной инициализации. Демо-данные генерируются автоматически; дашборд заполняется в течение первых циклов агрегации.

- [Movie Service — Swagger](http://localhost:8051/docs)
- [Aggregation Service — Swagger](http://localhost:8052/docs)
- [Grafana — Online Cinema](http://localhost:3050/d/cinema/online-cinema)

Остановка: `docker compose down`. Данные остаются в именованных volumes. Порты доступны только на localhost; учётные данные в Compose предназначены для локального стенда.

## API

| Запрос | Результат |
|---|---|
| `POST :8051/events` с JSON по [схеме Avro](schemas/movie-event.v1.avsc) | `201` и `event_id` после Kafka ACK, `422` при невалидном событии, `503` при сбое записи |
| `POST :8052/aggregations/YYYY-MM-DD` | Пересчёт метрик за дату UTC |
| `POST :8052/exports/YYYY-MM-DD` | Экспорт готовых метрик за завершённый день; `404`, если агрегатов нет |

Пример публикации:

```bash
curl -f http://localhost:8051/events -H 'Content-Type: application/json' -d '{
  "event_id": "ecff70c6-ed33-48ec-a505-5a8e28598e35",
  "user_id": "viewer-1",
  "movie_id": "movie-01",
  "event_type": "VIEW_STARTED",
  "timestamp": "2026-11-13T12:00:00Z",
  "device_type": "TV",
  "session_id": "session-1",
  "progress_seconds": 0
}'
curl -f -X POST http://localhost:8052/aggregations/2026-11-13
curl -f -X POST http://localhost:8052/exports/2026-11-13
```

Агрегация видит события после записи в ClickHouse, которая происходит асинхронно. Если пересчёт сделан сразу после публикации, его можно повторить или дождаться расписания.

## Как устроено

- **Kafka.** Топик `movie-events`: 3 партиции, 3 реплики, `min.insync.replicas=2`, `acks=all`. Ключ `user_id` помещает события одного пользователя в одну партицию и сохраняет порядок записи его действий. Продюсер валидирует JSON и Avro, пишет с идемпотентностью и повторяет сбои с экспоненциальной задержкой. Формат — Avro с идентификатором схемы; в Schema Registry зарегистрирована версия 1 субъекта `movie-events-value`, режим BACKWARD.
- **ClickHouse.** Kafka Engine читает AvroConfluent, materialized view переносит данные в `raw_events`. Месячные партиции и сортировка по дате и пользователю подходят для дневных выборок. ReplacingMergeTree и `FINAL` убирают точные повторы событий при повторном потреблении.
- **Метрики.** DAU — уникальные пользователи по всем событиям дня. Среднее время — средний прогресс для `VIEW_FINISHED`. Топ — до 10 фильмов по числу `VIEW_STARTED`. Конверсия — завершения / старты за тот же день; при отсутствии стартов значение пустое. Это отношение событий за день, а не доля завершённых сессий.
- **Retention.** Когорта определяется первым `VIEW_STARTED` пользователя за всю историю. Day N — доля когорты с новым стартом просмотра ровно через N дней, включая D1/D7. Day 0 равен 100%; ещё не завершившиеся дни пусты. ClickHouse вычисляет когорты через `min`, `groupUniqArrayIf` и `sumForEach`. Grafana читает только `daily_aggregates`.
- **Пересчёт и экспорт.** ClickHouse хранит последний снимок дня, PostgreSQL обновляет строки по ключу «дата, метрика, измерение» через UPSERT. День попадает в очередь после завершения, а при изменении метрик отправляется повторно. Путь: `s3://movie-analytics/daily/YYYY-MM-DD/aggregates.json`. В файле есть все метрики, дата и время вычисления. Повтор перезаписывает тот же объект; при ошибке задача остаётся в очереди.

Интервалы настраиваются через переменные Compose: `DEMO_INTERVAL_SECONDS` (8; 0 отключает генератор), `AGGREGATION_INTERVAL_SECONDS` (60; 0 отключает расписание), `AGGREGATION_LOOKBACK_DAYS` (14; минимум 1). Сервис пересчитывает текущий день и указанное число прошлых дней, чтобы учитывать поздние события и дозревание когорт. Более раннюю дату можно пересчитать через API. Данные пользователей с префиксами `demo-` и `live-` синтетические и служат для демонстрации.

## Проверка

```bash
docker compose run --build --rm tests
```

Тест проверяет Schema Registry и репликацию, отклонение неверных событий, все поля после доставки в ClickHouse, порядок демо-сессий, контрольные значения метрик, D0–D7, идемпотентность, содержимое S3 и выполнение запросов всех панелей Grafana. События и даты изолируются от демо-данных, повторный запуск не требует очистки БД.

После запуска стенда можно проверить отказ одного брокера:

```bash
sh tests/failover.sh
```

Скрипт останавливает один брокер, проверяет публикацию и доставку до ClickHouse, затем возвращает брокер в кластер. При отказе двух узлов запись не подтверждается: остаётся меньше двух реплик и теряется кворум KRaft.
